# C4 diagrams

## Level 1 — System context

```mermaid
flowchart LR
  R[Renter / construction buyer] --> ERP[Equipment Rental Platform]
  M[Rental company manager] --> ERP
  O[Rental company owner] --> ERP
  A[Platform administrator] --> ERP
  ERP -. future .-> PSP[Marketplace payment provider]
  ERP -. future .-> Mail[Transactional email provider]
  ERP -. optional .-> LLM[LLM API]
```

## Level 2 — Containers

```mermaid
flowchart TB
  Browser[Browser / React TypeScript SPA] --> Edge[Nginx / TLS ingress]
  Edge --> API[Django REST API / modular monolith]
  API --> PG[(PostgreSQL)]
  API --> Cache[(Redis)]
  Cache --> Worker[Celery worker + beat]
  Worker --> PG
  API --> Object[Object storage — planned for uploaded media]
  API -. disabled .-> PSP[Payment service provider]
```

## Level 3 — booking module

```mermaid
flowchart TD
  HTTP[Booking API] --> Auth[Authentication / tenant checks]
  Auth --> Service[Booking application service]
  Service --> Quote[Decimal quote domain function]
  Service --> Tx[PostgreSQL transaction + asset row lock]
  Tx --> Booking[Booking snapshot row]
  Tx --> Block[AvailabilityBlock range row]
  Block --> Constraint[GiST exclusion constraint]
  Service --> Conflict[409 on overlap or key mismatch]
  Service --> Outbox[Transactional outbox — planned for side effects]
```

## Limitations

The diagrams describe intended and source-level boundaries, not proof that every container or module is deployed. Object storage, provider integrations, observability exporter and durable outbox dispatch are not wired in this tranche.
